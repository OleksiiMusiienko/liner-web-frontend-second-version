# Liner — Web Frontend

Вебзастосунок музичної стримінгової платформи Liner.

## 1. Призначення проєкту

Liner Web Frontend забезпечує взаємодію користувачів із музичною платформою через вебінтерфейс та REST API Liner Web Backend.

Плануються пошук музики, перегляд каталогу, відтворення аудіо, плейлисти, тексти пісень та особистий профіль. Інтеграція з каталогом і текстами здійснюватиметься через Web Backend. Спосіб отримання та відтворення аудіопотоку ще потребує перевірки.

## 4. Глобальні провайдери

Глобальні провайдери централізовано підключаються
через AppProviders.

```text
main.tsx
└── StrictMode
    └── AppProviders
        └── BrowserRouter
            └── QueryClientProvider
                └── App
                    └── AppRouter
```

BrowserRouter забезпечує контекст маршрутизації.

QueryClientProvider забезпечує доступ до серверних
даних, кешування та управління станами запитів.

## 5. Маршрутизація

Маршрутизація централізована у файлі AppRouter.tsx.

Адреси маршрутів визначаються у routes.constants.ts.

Для відображення вкладених маршрутів
використовуються Layouts та Outlet.

### Реалізовані маршрути

| Маршрут | Призначення |
|---|---|
| / | Головна сторінка |
| /login | Сторінка входу |
| /register | Сторінка реєстрації |
| * | Сторінка 404 |

Сторінки входу та реєстрації на поточному етапі
є базовими заготовками без бізнес-логіки.

Захищені маршрути та перевірка прав доступу
будуть реалізовані разом із механізмом авторизації.

## 6. Взаємодія з Backend

HTTP-запити виконуються через централізований
екземпляр Axios — httpClient.

```text
Page / Component
        ↓
       Hook
        ↓
     API method
        ↓
     httpClient
        ↓
    Backend API
```

Компоненти не виконують HTTP-запити напряму.

Базова адреса Backend визначається
через змінні середовища.

Початковий таймаут HTTP-запитів становить 10 секунд.

Серверні дані обробляються через TanStack Query.

### Перевірка з'єднання

Для перевірки взаємодії Frontend та Backend
реалізовано запит:

```http
GET /health
```

Очікувана відповідь:

```json
{
  "status": "ok"
}
```

На головній сторінці тимчасово відображається
результат перевірки з'єднання з Backend.

## 7. Обробка помилок

Помилки HTTP-запитів централізовано обробляються
через Axios Response Interceptor.

Основні файли:

- api/interceptors/error.interceptor.ts
- utils/apiError.ts
- types/api.types.ts

Успішні HTTP-відповіді передаються без змін.

Помилки Backend, Axios та мережеві помилки
приводяться до єдиного формату:

```typescript
interface ApiError {
  statusCode: number | null;
  message: string;
  code: string | null;
}
```

За відсутності HTTP-відповіді statusCode дорівнює null.

Механізми оновлення токенів та відновлення сесій
будуть реалізовані на етапі авторизації.

## 8. Змінні середовища

Створити файл .env на основі .env.example.

```dotenv
VITE_API_URL=http://localhost:3000
```

Змінні середовища централізовано отримуються
та перевіряються через Zod у файлі config/env.ts.

Файл .env не додається до Git.

Змінні з префіксом VITE_ доступні у браузері.
Заборонено зберігати в них секретні ключі,
паролі та інші конфіденційні дані.

- Git


```bash

```

## 13. GitFlow

Проєкт використовує спрощену модель GitFlow.

| Гілка | Призначення |
|---|---|
| main | Стабільна версія |
| develop | Основна гілка розробки |
| feature/* | Реалізація окремих завдань |

Розробка виконується в окремих feature-гілках.

Порядок роботи:

1. Оновлення develop.
2. Створення feature-гілки.
3. Реалізація функціональності.
4. Форматування та перевірка коду.
5. Запуск тестів.
6. Перевірка збірки.
7. Commit та Push.
8. Pull Request у develop.
9. Перевірка та Merge.
10. Видалення завершеної feature-гілки.

Прямі зміни в main та develop не виконуються
в межах звичайної розробки.

### Безперервна інтеграція (CI)

Конфігурація: `.github/workflows/ci.yml`.

Workflow `Frontend CI` запускається для push та Pull Request у гілки `main` і `develop`. Job `Frontend Quality Check` використовує Ubuntu, Node.js 24 та pnpm і виконує:

1. `pnpm install --frozen-lockfile`
2. `pnpm lint`
3. `pnpm typecheck`
4. `pnpm test`
5. `pnpm build`

Для `main` і `develop` налаштовано ruleset `protect-main-and-develop`: обов’язковий Pull Request, успішний `Frontend Quality Check`, актуальність гілки перед злиттям, заборона видалення та force push. Кількість обов’язкових схвалень — 0 для самостійної розробки.

Автоматичне розгортання застосунку на цьому етапі не описано та не входить до наявного workflow.
